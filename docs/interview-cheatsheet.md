## 失败处理（降级链 · 绝不裸崩）
工具异常→ToolResult(ok=False) → 线程池 10s 超时 → 弹窗 close_popup + 重试一次 → 15 步上限收尾 → LLM 挂→启发式意图+默认计划+模板兜底 → 设备断→自动重连

## 验证结果
- 单元/回归：**37 测试全绿**（mock LLM + FakeAdb，不依赖真机/Key）
- 评估：10 任务 × 3 次，失败归因四类 = 坐标不准 / 规划不合理 / 记忆没注入 / 弹窗 → 决定改 UI 定位 / prompt / 记忆注入 / 弹窗检测

## 框架选型（三段式必说）
1. **为什么 LangGraph**：CodeAct 不安全 + 要 checkpoint 恢复 + 要可测
2. **限制**：reducer 易踩坑 / 同步异步混用 / 版本 API 变动快
3. **绕开**：线性流程→for 循环；动态工具爆炸→function-calling 循环

## 元能力
- **判质量**：统一契约（ToolResult/schema）+ 显式失败路径 + 能脱离外部测
- **AI 放大**：AI 写初稿，我写测试戳坑（例：reducer 指数增长是 AI 写的、测试发现的）
- **负责**：没测就标「待测」，不编数字，讲清边界（向量检索刚接上、还在 SQLite 兜底）

## 高频追问 & 一句话应对
- "为什么不直接让 LLM 生成 ADB 命令？" → 不安全/不可观测/不能重试，固定工具集换回可控
- "RAG 召回率怎么优化？" → 我的项目不是文档 RAG，检索在偏好记忆+UI 定位；通用召回=混合检索+rerank+query 改写+评测驱动
- "chunk 怎么切？" → 没有文档语料，对应的是「记忆窗口管理」（滑动窗口 20 / 摘要阈值 12 / 偏好原子化）
- "LangGraph 有什么坑？" → reducer 语义、同步异步混用、版本迭代快
- "成功率多少？" → 37 测试全绿；端到端 10 任务待真机，不编数字
