## 1. 开发环境搭建

### 1.1 前置依赖



| 依赖      | 版本要求                  | 用途            |
| ------- | --------------------- | ------------- |
| Python  | ≥ 3.10                | 后端与 Agent 运行时 |
| Node.js | ≥ 18 LTS              | 前端构建          |
| ADB     | Platform Tools ≥ 34.0 | Android 设备控制  |
| Docker  | ≥ 24.0                | 容器化部署与评估环境    |
| Git     | ≥ 2.40                | 版本控制          |

### 1.2 后端环境



```
\# 1. 克隆仓库

git clone \<repo-url> && cd Droirun-agent

\# 2. 创建虚拟环境

python -m venv .venv

.venv\Scripts\activate        # Windows

\# source .venv/bin/activate   # macOS/Linux

\# 3. 安装依赖

pip install -r requirements.txt

pip install -r requirements-dev.txt   # 开发依赖（pytest/ruff/mypy）

\# 4. 配置环境变量

cp .env.example .env

\# 编辑 .env：填入 DASHSCOPE\_API\_KEY，可选配置 LANGFUSE\_\*、DRO\_API\_TOKEN

\# 5. 验证安装

python -c "import langgraph, fastapi, uvicorn; print('OK')"

pytest tests/ -x -q   # 应 37 项全绿
```

```
cd web/

npm install

npm run dev    # 开发服务器，默认 http://localhost:5173

npm run build  # 生产构建到 dist/
```

```

adb connect 192.168.1.10:5555

\# 验证设备可用

adb shell getprop ro.product.model

```

### 1.5 可选基础设施（Langfuse）

\# 访问 http://localhost:3000，默认账号 admin@example.com / password

## 2. 分支策略

### 2.1 分支模型

采用 **GitFlow 简化版**（Trunk-Based + Release Branch）：



| 分支   | 命名                                | 用途            | 保护                |
| ---- | --------------------------------- | ------------- | ----------------- |
| 主分支  | `main`                            | 生产就绪代码，始终可发布  | 受保护，禁止直接 push     |
| 开发分支 | `develop`                         | 集成分支，日常开发合并目标 | 受保护，PR 合并         |
| 功能分支 | `feature/<模块>-<简述>`               | 新功能开发         | 个人分支，可 force push |
| 修复分支 | `fix/<issue-id>-<简述>`             | Bug 修复        | 个人分支              |
| 发布分支 | `release/v<major>.<minor>`        | 发布准备，仅修 bug   | 受保护               |
| 热修复  | `hotfix/v<major>.<minor>.<patch>` | 生产紧急修复        | 受保护               |

### 2.2 工作流



```
feature/xxx ──PR──→ develop ──PR──→ release/v1.0 ──merge──→ main

&#x20;                     ↑                                    │

&#x20;                     └────────── hotfix/v1.0.1 ←──────────┘
```

**功能开发流程：**



1. 从 `develop` 切出 `feature/<模块>-<简述>`

2. 本地开发，频繁小提交（每提交一个逻辑单元）

3. 完成后提 PR 到 `develop`，至少 1 人 review

4. CI 通过（lint + test + build）后合并

5. 删除功能分支

**发布流程：**



1. 从 `develop` 切出 `release/v1.0`

2. 发布分支仅修 bug、改版本号、更新文档

3. 验证通过后合并到 `main`，打 tag `v1.0.0`

4. 同时将 release 分支合并回 `develop`

### 2.3 提交规范

采用 **Conventional Commits**：



```
\<type>(\<scope>): \<subject>

\<body>

\<footer>
```



| type       | 用途           |
| ---------- | ------------ |
| `feat`     | 新功能          |
| `fix`      | Bug 修复       |
| `perf`     | 性能优化         |
| `refactor` | 重构（不改变功能）    |
| `docs`     | 文档变更         |
| `test`     | 测试相关         |
| `ci`       | CI/CD 配置     |
| `chore`    | 构建 / 依赖 / 工具 |
| `revert`   | 回滚           |

**示例：**



```
feat(agent): 实现 Manager-Executor 动态反馈环

\- 新增 manager\_node 与 executor\_node 分离

\- 接入 SoM 元素索引

\- 单任务 LLM 调用数从 12+ 降至 4-6 次

Closes #12
```

## 3. 代码规范

### 3.1 Python 规范



| 工具         | 配置                                    | 用途                     |
| ---------- | ------------------------------------- | ---------------------- |
| Ruff       | `line-length = 100`                   | lint + import 排序 + 格式化 |
| mypy       | `--strict`（核心模块）                      | 类型检查                   |
| pytest     | `--cov=src --cov-report=term-missing` | 单元测试 + 覆盖率             |
| pre-commit | 自动运行 ruff + mypy                      | 提交前检查                  |

**代码风格：**



* 类型注解：所有公共函数必须有完整类型注解（参数 + 返回值）

* 异常：禁止裸 `except:`，捕获具体异常；工具执行失败返回 `ToolResult(success=False)` 不抛异常

* 日志：使用 `structlog` 结构化日志，禁止 `print()`；日志包含 `thread_id`、`step`、`tool` 等上下文

* 配置：所有配置通过 `pydantic-settings` 从环境变量读取，禁止硬编码 API Key / 路径

* 异步：IO 密集操作（LLM 调用、ADB 命令）使用 `async/await`

**目录结构约定：**



```
src/

├── agent/          # LangGraph 编排（graph.py, nodes/, state.py）

├── tools/          # 原子工具（base.py, actions/, skills/）

├── device/         # 设备池与 ADB（device\_pool.py, adb\_client.py）

├── llm/            # 模型网关（client.py, router.py, prompts/）

├── memory/         # 记忆层（store.py, long\_term.py, profile.py）

├── api/            # FastAPI 路由（routes/, schemas/, middleware/）

├── observability/  # 可观测性（langfuse.py, metrics.py）

└── core/           # 公共组件（config.py, exceptions.py, utils/）
```

### 3.2 前端规范



| 工具                  | 用途       |
| ------------------- | -------- |
| ESLint + Prettier   | 代码规范与格式化 |
| TypeScript strict   | 严格类型检查   |
| Husky + lint-staged | 提交前自动格式化 |

**代码风格：**



* 组件：函数组件 + Hooks，禁止 Class 组件；组件文件 PascalCase

* 状态：全局状态用 Zustand，局部状态用 `useState`/`useReducer`；禁止 prop drilling 超过 3 层

* 样式：优先 Tailwind 工具类，复杂样式用 CSS Modules；设计令牌统一在 `tokens.css`

* API 调用：封装 `useSSE()` hook 处理流式连接、重连、错误；REST 用 `fetch` 封装

* 命名：事件处理 `handleXxx`，布尔变量 `isXxx`/`hasXxx`，自定义 Hook `useXxx`

### 3.3 文档规范



* 代码注释：公共 API 必须有 docstring（Google 风格），复杂算法必须有行内注释

* README：每个模块目录下有 `README.md` 说明职责、关键接口、使用示例

* ADR：重大技术决策记录在 `docs/adr/ADR-NNN-标题.md`

* API 文档：FastAPI 自动生成 `/docs`（Swagger），所有端点必须有 `summary` + `description` + 响应模型

## 4. 测试策略

### 4.1 测试金字塔



```
&#x20;       /\  E2E 评估 (AndroidWorld 任务集, 每次发布)

&#x20;      /--\ 集成测试 (设备+Agent+API, CI 每日)

&#x20;     /----\ 单元测试 (每个函数/类, CI 每次提交)

&#x20;    /------\\
```

### 4.2 单元测试



* **框架：** pytest + pytest-asyncio

* **覆盖率：** 核心模块（agent/tools/device/llm）≥ 80%，整体 ≥ 70%

* **命名：** `test_<模块>_<场景>_<预期>.py`

* **Mock：** LLM 调用用 `respx` mock HTTP；ADB 命令用 mock subprocess；设备用 fake device

* **要求：** 每个 PR 新增代码必须附带对应测试，CI 覆盖率不下降

**示例：**



```
\# tests/agent/test\_manager\_node.py

@pytest.mark.asyncio

async def test\_manager\_node\_returns\_action\_type():

&#x20;   state = GraphState(screenshot=b"...", a11y\_tree="\<xml>...", task="比价耳机")

&#x20;   result = await manager\_node(state, llm\_client=mock\_llm)

&#x20;   assert result\["next\_action"] in {"click", "type", "swipe", "done"}

&#x20;   assert result\["sub\_goal"] is not None
```

### 4.3 集成测试



* **范围：** FastAPI → Agent → 工具 → ADB（连接真实模拟器）

* **触发：** CI 每日夜间运行，或手动 `/test-integration` 评论触发

* **用例：** 核心场景（比价 / 找相似 / 推荐）各 3-5 条，验证端到端流程

* **环境：** 专用模拟器镜像，预装淘宝 / 京东，固定账号登录态

### 4.4 评估测试（E2E）



* **基准：** AndroidWorld（116 任务跨 20 应用）+ 自建电商评估集（50 任务）

* **指标：** 任务成功率、平均步数、平均时长、LLM 调用数、token 消耗

* **触发：** 每次合并到 `develop` 后自动运行评估集（子集 20 任务），每次发布运行全集

* **报告：** 评估结果写入 `docs/evaluation/`，对比基线，成功率下降则阻断发布

* **回放：** 失败任务自动保存 trace + 截图序列，可在 Langfuse 中回放

### 4.5 回归测试



* 每个修复的 Bug 必须先写一个复现测试（红），再修复（绿），测试永久保留防回归

* 核心场景有 golden test 集，每次 CI 运行对比输出差异

## 5. CI/CD 流程

### 5.1 CI 流水线（每次 PR /push）



```
┌──────────────────────────────────────────────┐

│ 1. 代码检查                                    │

│    - ruff lint + format check                 │

│    - mypy 类型检查（核心模块）                  │

│    - 前端 ESLint + Prettier check             │

├──────────────────────────────────────────────┤

│ 2. 单元测试                                    │

│    - pytest（37+ 项，增量）                    │

│    - 覆盖率检查（不低于基线）                   │

│    - 前端 vitest                              │

├──────────────────────────────────────────────┤

│ 3. 构建验证                                    │

│    - Python 包构建（sdist + wheel）            │

│    - 前端 npm run build                       │

│    - Docker 镜像构建（不推送）                  │

├──────────────────────────────────────────────┤

│ 4. 安全扫描                                    │

│    - pip-audit（依赖漏洞）                     │

│    - npm audit                                │

│    - 密钥扫描（gitleaks）                      │

└──────────────────────────────────────────────┘

全部通过 → PR 可合并
```

### 5.2 夜间流水线（每日）



```
┌──────────────────────────────────────────────┐

│ 1. 集成测试（真实模拟器）                       │

│ 2. 评估集子集（20 任务）                        │

│ 3. 性能基准（单任务时长 vs 基线）               │

│ 4. 报告生成 → 飞书群通知                        │

└──────────────────────────────────────────────┘
```

### 5.3 发布流水线（tag 触发）



```
git tag v1.0.0 && git push --tags

&#x20;   │

&#x20;   ▼

┌──────────────────────────────────────────────┐

│ 1. 全量评估集（AndroidWorld + 电商集 50 任务）  │

│ 2. 成功率 ≥ 基线？→ 否则阻断发布                │

│ 3. 构建 Docker 镜像并推送到 registry            │

│    - dro-app:v1.0.0                           │

│    - dro-frontend:v1.0.0                      │

```

| prod    | 生产    | tag 手动审批       | 生产设备池 + 用户数据   |

## 6. 发布流程

### 6.1 发布检查清单

发布前逐项确认，全部通过方可发布：



* [ ] 代码已合并到 `release/vX.Y` 分支

* [ ] CI 全绿（lint + 单测 + 构建 + 安全扫描）

* [ ] 集成测试通过

* [ ] 全量评估集成功率 ≥ 上一版本（或下降在可接受范围并有说明）

* [ ] 性能指标达标（单任务时长、LLM 调用数）

* [ ] 数据库迁移脚本已准备并在 staging 验证

* [ ] 配置变更已更新 `.env.example` 和部署文档

* [ ] Release Notes 已编写（新功能、Bug 修复、Breaking Changes、升级指南）

* [ ] 回滚方案已确认

* [ ] 相关文档（PRD、架构设计、API 文档）已更新

### 6.2 发布步骤



1. **准备阶段（T-3 天）**

* 从 `develop` 切出 `release/vX.Y`

* 冻结功能，仅修 bug

* 更新版本号（`src/core/version.py`、`package.json`、`Chart.yaml`）

* 更新 CHANGELOG.md

1. **验证阶段（T-1 天）**

* 部署到 staging

* 运行全量评估集

* 核心场景人工回归

* 性能基准对比

1. **发布阶段（T 日）**

* 合并 release 到 `main`，打 tag `vX.Y.Z`

* 触发发布流水线

* 灰度部署（先 1 台设备池，观察 30 分钟）

* 全量部署

* 监控告警面板确认无异常

1. **发布后（T+1 天）**

* 观察生产指标（成功率、延迟、错误率）

* 收集用户反馈

* 将 release 分支合并回 `develop`

### 6.3 版本号规范

语义化版本 `MAJOR.MINOR.PATCH`：



* **MAJOR：** 不兼容的 API 变更（如状态图结构重构、工具接口变更）

* **MINOR：** 向下兼容的功能新增（如新工具、新场景、前端新页面）

* **PATCH：** 向下兼容的 Bug 修复与性能优化

## 7. 回滚策略

### 7.1 回滚触发条件



* 生产任务成功率下降超过 10%

* 错误率超过 5% 持续 5 分钟

* P95 延迟超过基线 2 倍

* 出现数据错乱（设备串账号、任务状态异常）

* 安全漏洞被利用

### 7.2 回滚方式



| 场景      | 回滚方式                                                            | RTO     |
| ------- | --------------------------------------------------------------- | ------- |
| 应用代码问题  | `docker compose down && docker compose up -d dro-app:<上一版本tag>` | < 5 分钟  |
| 数据库迁移问题 | 回滚迁移脚本 + 恢复备份（发布前自动备份）                                          | < 15 分钟 |
| 前端问题    | 回滚静态资源到上一版本（Nginx 切换目录）                                         | < 2 分钟  |
| 模型配置问题  | 切换 `models.json` 到上一版本，热重载                                      | < 1 分钟  |
| 设备池问题   | 摘除异常设备，流量路由到健康设备                                                | < 3 分钟  |

### 7.3 回滚后处理



1. 在 staging 环境复现问题

2. 修复后走正常发布流程（hotfix 分支）

3. 编写事故复盘文档（时间线、根因、影响、改进措施）

4. 更新测试用例覆盖该场景

## 8. 监控与告警

### 8.1 关键指标



| 指标             | 告警阈值     | 通知方式    |
| -------------- | -------- | ------- |
| 任务成功率（5min 滑动） | < 60%    | 飞书 + 电话 |
| LLM 错误率（5min）  | > 10%    | 飞书      |
| 设备在线数          | < 预期 50% | 飞书      |
| API P95 延迟     | > 10s    | 飞书      |
| SSE 连接断开率      | > 20%    | 飞书      |
| 磁盘使用率          | > 85%    | 飞书      |

### 8.2 日志规范



* 结构化 JSON 日志，字段：`timestamp`、`level`、`thread_id`、`step`、`tool`、`message`、`duration_ms`

* 日志级别：`DEBUG`（开发）、`INFO`（生产默认）、`WARNING`（可恢复异常）、`ERROR`（需关注）

* 敏感信息（API Key、用户输入中的隐私）自动脱敏

* 日志保留 30 天，评估 trace 永久保留

## 9. 协作规范

### 9.1 PR 规范



* PR 标题遵循 Conventional Commits 格式

* PR 描述包含：变更内容、测试方式、截图 / 录屏（前端变更）、关联 issue

* 至少 1 人 approve 方可合并；核心模块（agent/graph、device/device\_pool）需 2 人

* CI 必须全绿

* PR 大小建议 < 400 行变更，超过则拆分

### 9.2 代码 Review 检查清单

Reviewer 重点关注：



* [ ] 功能正确性：逻辑是否正确，边界条件是否处理

* [ ] 错误处理：异常是否捕获，失败是否有降级

* [ ] 性能：是否有不必要的 LLM 调用、固定 sleep、重复计算

* [ ] 安全：是否有注入风险、敏感信息泄露

* [ ] 可测试性：是否容易写单元测试，是否有硬编码依赖

* [ ] 命名与可读性：变量 / 函数命名是否清晰，复杂逻辑是否有注释

* [ ] 测试：是否有对应测试，覆盖率是否足够

### 9.3 任务管理



* 使用 GitHub Issues 管理任务，每个功能 / 修复对应一个 issue

* Issue 标签：`feature`、`bug`、`perf`、`docs`、`priority:P0/P1/P2`

* 迭代规划：每 2 周一个 Sprint，Sprint 开始前梳理 backlog，结束后复盘

* 每日站会：15 分钟，同步进展、阻塞、今日计划
