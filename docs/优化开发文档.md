# Dro / WorkBuddy Agent 优化开发文档

> 范围：基于当前 `v2/` 架构（LangGraph + 工具化 ADB + 四层记忆 + FastAPI 内嵌 UI），
> 面向 workbuddy 产品方向（从「电商比价助手」泛化为「可扩展的手机操作 Agent」），
> 分别输出 **性能优化、功能扩展、前端优化** 三部分的工程实施方案。
>
> 定位：本文档是「可执行的开发任务清单」，每条给出 现状问题 → 方案 → 预期收益 → 涉及文件 → 优先级。

---

## 0. 现状诊断（一句话结论）

| 维度 | 现状 | 主要瓶颈 / 缺口 |
| --- | --- | --- |
| 编排 | LangGraph 状态图，节点同步实现 + `asyncio.to_thread` | 每次节点都新建 LLM 客户端与记忆实例 |
| 工具 | 11 个原子工具，`execute_tool` 线程池超时兜底 | 每个工具调用都新建 **ThreadPoolExecutor** |
| 设备 | `adb_client.py` 子进程封装 | 每次工具都 `adb devices` 探测 + 反复 `_screen_size`；大量固定 `time.sleep` |
| 记忆 | 四层记忆，SQLite 兜底 + Qdrant/PG 可选 | 每节点重复建 `SqliteStore`（每次开 2 个连接）；每轮都做偏好提取 LLM 调用 |
| LLM | 同步 `httpx.post`，无连接复用、无流式 | 单任务 10+ 次 LLM 调用，`_decide_finish` 每步都再调一次 LLM |
| API | 任务 + 聊天两套接口 | 前端 **900ms/1500ms 轮询**；`TASK_STORE`/`SESSION_STORE` 纯内存不持久 |
| 前端 | 两页 HTML 以三引号字符串**内嵌在 `v2/api.py`**（约 1100 行） | 无法分离维护、无缓存、无实时推送、两套重复 CSS |

**结论**：架构方向正确（工具化、checkpoint、记忆解耦），但存在「连接/线程/实例不复用」「固定 sleep 堆积」「每步多一次 LLM」「轮询 + 内存态」四类系统性开销，是优化的主战场。

## 1. 性能优化

### 1.1 LLM 客户端复用与连接池（P0，收益：单任务省 30~50% 网络往返）

**现状**：
- `v2/graph.py:73` `_get_runtime_llm()` 每次构造 `LLMClient()`；在 `intent_node(159)`、`planner_node(256)`、`_decide_finish(345)`、`result_node(612)` 各自新建。
- `v2/llm.py:51` 用 `httpx.post(...)` 每次新建连接，无 keep-alive，请求完成即断开 TLS。

**方案**：
1. `LLMClient` 内部持有 **模块级共享 `httpx.Client`**（`FollowRedirects` + `limits` 连接池上限），`chat/json/image/embed` 复用同一 client；显式 `close()` 交由进程退出处理。
2. 提供 `get_runtime_llm()` 改为 **单例**（惰性 + 线程安全），替换 graph 内 4 处 `_get_runtime_llm()` 调用。
3. 连续同义 LLM 调用做 **结果缓存**：意图识别对相同 `(user_message, task_type, recent_hash, memory_hash)` 命中即复用（温度 0.1 的场景缓存命中率高、成本收益明显）。

**预期**：把「每步建连接 + TLS 握手」降为常驻连接；意图分类缓存进一步去掉热路径模型调用。
**涉及**：`v2/llm.py`、`v2/graph.py`。

### 1.2 工具执行器：线程池复用（P0）

**现状**：`v2/tools/base.py:104` `with ThreadPoolExecutor(max_workers=1)` —— **每次 execute_tool 都创建并销毁一个线程池**。一个比价任务约 7~9 步，意味着 7~9 次线程池创建销毁。

**方案**：模块级共享 `_EXECUTOR = ThreadPoolExecutor(max_workers=4)`，`execute_tool` 直接 `_EXECUTOR.submit(...)`；超时逻辑保持不变（`future.result(timeout=...)`）。并发任务也能复用同一池子。
**预期**：去掉每步 ~ms 级的池创建开销与线程重开；配合 1.3 降低整体步时。
**涉及**：`v2/tools/base.py`。

### 1.3 ADB 层：设备态缓存 + 降固定 sleep（P0，收益最大）

**现状**：
- 每个工具入口都调 `adb.ensure_online()`（`v2/adb_client.py:104`），内部 `adb devices` 子进程 + 潜在 `disconnect/connect`，**每步重复**。
- `adb._screen_size()`（`v2/adb_client.py:276`）每次 `wm size` 子进程；`click_product`/`search_product`/`swipe` 每步都要调一次甚至多次。
- 大量固定 `time.sleep`：`search_product`（1.2+0.6+2.0s）、`open_app`（3s）、`click_product`（2s）、`swipe`（每下 1s）、`go_back`（1s）。单次比价累计固定等待可达 15~20s。

**方案**：
1. 模块级缓存 `screen_size`（设备分辨率不变，首得即缓存）；`ensure_online` 加 **TTL 在线态缓存**（如 3s 内不再探测），工具内由「执行失败再触发重连」兜底。
2. 将固定 `time.sleep` 替换为 **「轮询等待状态就绪」**：搜索后轮询 `dump_ui` 直到出现搜索框/结果列表节点（带上限），`open_app` 后轮询当前焦点包名到位。把等待从「拍脑袋拍 2s」改成「等到真好了」，平均缩短且更稳。
3. 抽取统一的 `wait_for(predicate, timeout, interval)` 辅助函数，供各工具复用。
4. `screencap` 三步（screencap→pull→rm）可合并为 `adb exec-out screencap -p` **免落地直接拉流**，省一次写盘 + 一次 rm 子进程。

**预期**：固定等待 → 状态等待，单任务端到端时长预计下降 **30~50%**；子进程调用次数也明显下降。
**涉及**：`v2/adb_client.py`、`v2/tools/search_product.py`、`open_app.py`、`click_product.py`、`gesture.py`、`extract_info.py`、`screenshot.py`。

### 1.4 记忆系统：连接/实例单例化 + 偏好提取异步化（P0）

**现状**：
- `v2/memory.py:431` `_default_store()` 每次返回**新** `SqliteStore`；`SqliteStore.__init__`（`:58`、`:61`）每次开 **2 个** SQLite 连接。
- `graph.py` 中 `intent_node`、`planner_node`、`result_node`、`_decide_finish`、`extract_and_store_preferences` 频繁 `MemoryManager(...)`，每次 `__init__` 还**立刻尝试** `LongTermMemory`（连 Qdrant）与 `ProfileStore`（连 PostgreSQL）。
- `v2/graph.py:245` 每个 `intent_node` 都同步调用 `extract_and_store_preferences` —— **每轮一次偏好提取 LLM 调用**，阻塞意图节点。

**方案**：
1. `SqliteStore` 做成**进程级单例**（`functools.lru_cache` 或模块级全局），`MemoryManager` 复用同一 store；把 `self.conn` 与 `self._lock` 收敛为「读连接 + 写锁连接」各一，避免每次 2 连。
2. `LongTermMemory._qdrant` / `ProfileStore._pg` 改为**惰性连接 + 连接复用**（当前已经是惰性 import，但连接对象每次新建），失败降级结果也缓存。
3. `extract_and_store_preferences` 从「每轮同步」改为 **fire-and-forget 后台任务**（不进关键执行路径），或按「文本含明显偏好的关键词才触发」降频；偏好写入放到结果节点末尾。
4. `build_prompt` 里 `long_term.search()` 对 `embed + qdrant.query` 做**结果缓存**（同 user_id + 同 query 短时间内复用）。

**预期**：消除每节点重建 SQLite/Qdrant/PG 的开销；去掉每轮 1 次偏好提取 LLM 调用。
**涉及**：`v2/memory.py`、`v2/graph.py`。

### 1.5 ReAct 提前结束判定：规则优先，LLM 兜底（P1）

**现状**：`v2/graph.py:481-489` 每个**成功**工具步骤后都调用 `_decide_finish` → 一次 LLM。比价任务 7 步 ≈ 7 次额外 LLM，叠加规划/结果/意图/偏好，单任务 LLM 调用数轻松 12+。

**方案**：
1. 先用**确定性规则**判定（已在 `_decide_finish` 注释里写明的规则）：有预算上限时已采集到预算内商品 → finish；比价任务两平台都采集到 → finish；`collected` 数量达阈值（如 ≥3）→ finish。
2. 仅当规则**不命中且已采集数据足以判断**时才降级调 LLM；并给 LLM finish 决策设定**步级别的节流**（如前 3 步不调）。

**预期**：单任务 LLM 调用从 12+ 降到 4~6，显著减少延迟与 token 成本。
**涉及**：`v2/graph.py`。

### 1.6 Checkpoint / 并发（P1）

**现状**：`v2/graph.py:758-776` 全局单例 `SqliteSaver`，底层是**一条** `check_same_thread=False` 的 SQLite 连接跨线程共享；多个聊天会话并发写 checkpoint 时会争锁、存在跨线程风险。

**方案**：
1. checkpoint 迁移到 **`langgraph.checkpoint.sqlite.aio.AsyncSqliteSaver`**（若当前版本支持）或维护一个**连接池**，避免单连接跨线程写入。
2. 设备是单例资源：在 `TaskRunner` 增加**设备互斥锁**（`threading.Lock` / `asyncio.Lock`），同一时间只允许一个任务驱动设备，其余任务进入队列；避免多用户「抢设备」导致的乱序点击。
3. `TASK_STORE`/`SESSION_STORE` 由纯内存迁到 SQLite（`tasks` / `sessions` 表），支撑重启后任务列表仍可见（见 §2.6）。

**预期**：并发场景不串数据、不崩；任务状态可持久、可恢复。
**涉及**：`v2/graph.py`、`v2/api.py`。

### 1.7 API / 轮询性能（P1）

**现状**：
- 聊天页 `v2/api.py:604` 每 900ms 轮询 `/events`；控制台 `:1233` 每 1500ms 轮询 `/tasks/{id}`。每次轮询 `aget_state → asyncio.to_thread → SqliteSaver.get_state`（读 SQLite）。
- `v2/api.py:100` `_list_sessions` 对每个会话发起 **2 次额外查询**（N+1）。
- 视觉图片 `v2/llm.py:76` 每次整图 base64 编码，未降采样（1080×2400 原图）。

**方案**：
1. 实时进度从**轮询改为 SSE / WebSocket**（见 §3.2），从「N 次轮询」降到「一次长连接 + 事件推送」，前端与后端同时受益。
2. `_list_sessions` 改写为**单条 SQL**（`JOIN` 最近消息 + `COUNT`），消除 N+1。
3. 图片上传/视觉前**降采样**（如最长边缩到 1024、转 JPEG），减少 base64 体积与视觉模型 token。

**预期**：轮询改推送后服务端读 checkpoint 频次下降 >90%；会话列表秒开。
**涉及**：`v2/api.py`、`v2/llm.py`、`v2/vision.py`。

## 2. 功能扩展

### 2.0 产品定位：workbuddy 方向
在电商比价能力之外，把 `adb_client` + 工具注册表 + 视觉服务作为**可插拔的通用手机操作底座**，新增一批「生活助手」工具（打开应用/拨号/发消息/查天气/定闹钟等），使 workbuddy 从「购物 Agent」演进为「手机 Agent」。下述扩展均沿用现有工具化框架，代价低、收益高。

### 2.1 代下单 / 加购流程（P0，对应需求文档）
**需求**：需求文档明确要求「最后输出是否需要代下单的选项，供用户自由选择」。
**现状**：`result_node` 只输出 `show_checkout_option` 布尔位，**无下单/加购工具**。
**方案**：
1. 新增工具 `add_to_cart(index)`、`view_cart()`、`confirm_order(address, pay_auth)`（后两步为「确认式」），纳入 `PLANNER_SYSTEM`/`REACT_SYSTEM`。
2. `result_node` 返回结构化 `checkout_options`（含 token/候选商品 id），前端弹出「是否需要代下单」卡片。
3. **安全护栏**：下单操作必须经前端二次确认 + 会话级白名单，未确认绝不点「确认支付」。

### 2.2 商品链接 / 商品 ID 提取 + 跳转（P0）
**现状**：`extract_info` 只提取文案，`link` 字段几乎恒为空。
**方案**：
1. `extract_info` 扩展 prompt 要求视觉模型同时输出每个商品卡片的**相对坐标**，`click_product` 之后新增 `get_product_deeplink()`：进入详情页 → `dumpsys` 抓 `act/deeplink/商品 id` → 拼接 `taobao://item?id=` 或 `item.m.jd.com/product/{sku}`。
2. 前端商品卡片展示「打开」按钮，点击跳转深链；无法拿到深链时退化为商品关键词搜索链接。

### 2.3 最优方案评分算法（P0，对应需求文档）
**需求**：「最优方案评判方式：购买量、好评率、价格（占比最高）、是否有运费、退货是否有运费险」。
**现状**：`result_node` 的最终推荐依赖 LLM 文本，无确定性打分。
**方案**：在 `result_node` 前插入确定性 `rank_products()`：
```
score = w_price * normalize(1 / price)
      + w_sales * normalize(sales)
      + w_rating * (rating - 4.0)
      - w_shipping * (has_shipping_fee ? 1 : 0)
      + w_insurance * (has_return_insurance ? 1 : 0)
```
权重默认 `price 0.5 / sales 0.2 / rating 0.15 / shipping 0.1 / insurance 0.05`，可配置；**先算分，再丢给 LLM 生成解释文字**，保证「最便宜/最优」结论可复现、可解释、可测试。

### 2.4 以图搜图（P1）
**现状**：有 `image_path` 时强制 `find_similar`，但实际搜索仍用 `search_product` 文本，**未真正用图**。
**方案**：新增 `image_search(image_path)` 工具：进入淘宝/京东 → 点「相机/扫一扫」入口（UI 定位 + 固定坐标兜底）→ 调起系统图库/相册上传已保存图片 → 等待识图结果 → 复用 `extract_info` 采集。

### 2.5 模型选择（ds / 千问）+ 多供应商（P0，对应需求文档前端项 1）
**现状**：配置上有 `qwen_model`/`deepseek_model`，但**接口未暴露模型参数**，前端无法切换。
**方案**：
1. `TaskRequest`/`ChatRequest` 增加 `model: str = ""`，落到 `LLMClient(model=…)`；`llm.need_deepseek_model` 已预留映射。
2. 前端两个页面加「模型选择」下拉（千问 / DeepSeek / 自动），会话语义下默认「自动」。
3. 保留不同供应商可插拔（后续接 Gemini/Claude 仅需加 `api_base + key` 解析）。

### 2.6 任务队列 / 多设备 / 持久化（P0）
**现状**：任务以 `asyncio.create_task` 直跑，多用户并抢同一设备；`TASK_STORE`/`SESSION_STORE` 内存态，重启即丢。
**方案**：
1. 设备互斥锁 + **FIFO 任务队列**，超过 1 台设备时可做设备池路由（`device_serial` 可随任务指定）。
2. `TASK_STORE`/`SESSION_STORE` 落 SQLite（`tasks`/`sessions` 表），`/v2/tasks`、`/v2/chat/sessions` 读库，支撑重启后恢复显示与 `resume`。

### 2.7 可观测性（P1）
**现状**：全项目 `print()`，无结构化日志，无法回答「每步花了多久」「token 花了多少」「哪类工具成功率低」。
**方案**：
1. 标准库 `logging` + 结构化字段，替代散落 `print`；每节点/工具/LLM 记录 `latency_ms`、`ok`、`model`、`tokens`（从 LLM 响应 `usage` 读取）。
2. 新增 `/v2/metrics`（Prometheus 文本格式）暴露：请求数、成功率、平均步时、工具成功率、LLM 时延分位、token 消耗。
3. 用这些指标回填 `docs/evaluation.md`（当前「每个任务跑 3 次」可自动统计）。

### 2.8 安全与鉴权（P1）
**现状**：所有接口无鉴权、无上传大小限制（仅限扩展名）。
**方案**：可选 `DRO_API_TOKEN`（Bearer 校验中间件，缺省关闭以保零配置可用）；`/v2/upload` 加文件大小上限（如 8MB）+ 魔数校验；前端渲染已用 `esc`/`escapeHtml`，保持。

### 2.9 记忆增强（P1）
- 会话摘要触发阈值可配并**在结果节点末尾触发**（当前 `get_history` 内隐式触发，切入点不稳）。
- 长期偏好支持**显式更正**（用户说「其实我喜欢黑的」要能覆盖而非追加）。
- 向量检索用**嵌入式本地向量库**（如 `sqlite-vec`）替代对 Qdrant 的强依赖，保持零外部依赖可跑。

## 3. 前端优化

### 3.1 页面代码工程化（P0，可维护性）
**现状**：两页 HTML/CSS/JS 以三引号**内嵌**在 `v2/api.py`（`_render_chat_page` `:146` 起、`_render_home_page` `:715` 起），共约 1100 行；改动需动 `.py`，无语法高亮、无缓存。
**方案**：
1. 抽到 `v2/templates/`（`chat.html`、`home.html`）+ `v2/static/`（`app.css`、`chat.js`、`home.js`）。
2. `FastAPI` 挂 `StaticFiles` + `Jinja2Templates`；给静态资源加 `Cache-Control`（对带 hash 的文件 `max-age=31536000`）。
3. 两页共用一套设计令牌（CSS 变量），去掉重复的 `:root` 与按钮/状态/商品卡片样式。

### 3.2 实时化：轮询 → SSE / WebSocket（P0）
**现状**：聊天 900ms 轮询 `/events`，控制台 1500ms 轮询 `/tasks/{id}`（§1.7）。
**方案**：
1. `/v2/chat/{session_id}/stream` 用 **SSE**（`text/event-stream`），`/v2/tasks/{thread_id}/events` 同样 SSE 化；工具每步完成即推 `progress`/`result` 事件。
2. 前端 `EventSource` 消费，后退化为现有轮询（渐进增强）。
**收益**：进度显示从「最多迟 900/1500ms」变为「即时」；服务端消除高频轮询读库。

### 3.3 设计系统统一 + 暗色模式 + 响应式（P1）
- 合并两页样式为单一 `app.css`，规定 色板/圆角/阴影/间距 令牌。
- 增加 **暗色模式**（`prefers-color-scheme` + 手动切换）；当前两页均为浅色且令牌重复。
- 聊天页已部分响应式（`max-width:860px` 主列），补全移动端：小屏隐藏/折叠会话侧栏、输入区吸底。

### 3.4 商品卡片与交互增强（P0）
- 商品卡增加 **商品图片**（`extract_info` 额外切出缩略图 → 前端 `<img>`，找不到给占位）与 **「打开链接」** 按钮（§2.2 深链）。
- 结果区增加 **「需要代下单」卡片**（§2.1）与 **「导出比较结果」**（JSON/CSV）。
- 控制台执行日志从纯文本 `safeJson` 升级为**步骤时间线**（每步：工具名、耗时、o/x、可选截图缩略图，截图路径已由 `tool_log.data.screenshot` 提供）。

### 3.5 交互体验（P1）
- 增加 **打字机 / 流式渲染** 最终回复（配合 SSE 分片）。
- 发送中按钮禁用与「停止」态更清晰；`session.activeTurn` 下对图片/文本输入给明确反馈。
- 会话列表支持**删除/重命名**（后端加对应接口）。
- 长会话历史做**虚拟列表 / 分页**，避免一次性渲染巨量 DOM。

### 3.6 前端性能与安全（P1）
- 静态资源按 hash 命名并长缓存；`img` 附件用 `objectURL` 记得 `revokeObjectURL` 防内存泄漏。
- 保留并统一 `esc`/`escapeHtml`；新增内容（深链、图片）一律转义后再插入。
- 分页会话列表 + 历史，避免 `_list_sessions` 全量前端渲染。

## 5. 风险与注意点

1. **单设备串行化**：设备锁引入后多个用户任务排队，需给队列长度/超时上限，避免饥饿；前端展示「排队中」状态。
2. **SQLite 并发写**：checkpoint/记忆/任务三库写并发是稳定性重点，建议每个库独立连接 + WAL 模式（`PRAGMA journal_mode=WAL`）。
3. **深链/下单涉及真实资金**：代下单必须二次确认 + 白名单，测试阶段只打「加购」不打「支付」。
4. **视觉/坐标不稳定**：仍保留「UI 元素优先、坐标兜底」策略，新增工具沿用同一套 `ui.py` 定位，避免回退到绝对的死坐标。
5. **模型可插拔**：多供应商只做 `api_base + key` 解析，不要在业务代码写死供应商逻辑。
